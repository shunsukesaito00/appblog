# 文章のAI感を避けるルール（執筆ボイス）

ブログ記事・紹介文・サイト上の長文を書く／直すときは、**作業開始前に必ずこのファイルを読み、全文で守る。**

対象: `src/content/blog/**`、収益報告、How-to、アプリ紹介、About 等の本文・`title` / `description`。  
対象外: CSS・レイアウト・コンポーネント構成（見た目のAI感は別タスク）。

---

## 1. 定義

**AI感（文章）** = 読んだあと「この人のメモ」ではなく「汎用で正しい説明文」に感じること。

- AIを使ったかどうかは問わない。
- **固有の数字・固有の状況・迷い・未完了**が残っていれば、AI感は弱い。
- **誰のブログに貼っても通じるきれいな文**は、AI感が強い。

**合格の目安:** 固有名詞と具体数字を消しても、別の個人開発ブログにそのまま貼れる段落は書き直す。

---

## 2. 書く前のチェック（必須）

記事に入る前に、次を1行でもよいので決める（本文か下書きメモに残す）。

1. **今月／今回の一言:** 感情や状況（例:「更新ほぼなしで落ちた」「ツール代の前では収益が消える」）
2. **根拠になる数字 or 事実:** スクショ・既存記事・ユーザー提示のみ。無いものは「未取得」
3. **まだ分かっていないこと:** 1つは残してよい（断定で埋めない）

これが無い原稿は、テンプレ感が出やすいので書き始めない。

---

## 3. 禁止（AI感が強い表現）

次は使わない。近い言い回しも避ける。

### 空のビジネス語

- 一気通貫 / 実践ポートフォリオ / 継続的に改善 / 収益化を目指すプロセス
- 戦略的に / 包括的に / シームレスに / 最適化を図る / 価値を提供する
- 〜をサポートします / 〜に役立ちます（中身なしの結び）
- 「個人開発×副業収益化」のような **記号だけの掛け合わせ見出し**（中身の数字がないとき）

### 定型の締め・煽り

- 「同じように頑張るあなたを応援します」「一緒に成長しましょう」
- 「今すぐ始めましょう」「必見」「徹底解説」「完全ガイド」（How-toでも過剰なら削る）
- 絵文字の装飾的連打、感嘆符の連打

### 偽のバランス・偽の結論

- 悪い数字の直後に、根拠のない明るい逆転で着地する
- データが無いのに因果を断定する（「だから伸びた」「だから落ちた」）
- すべての論点をきれいに閉じる（未解決をゼロにしない）

### SEOのための中身のない列挙

- title / description にキーワードを詰めすぎて、一文として不自然になること
- 「〜とは？」「メリット・デメリット」を、読者の問いに関係なく足すこと

---

## 4. 推奨（AI感が弱い表現）

### 具体

- 金額・件数・期間を書く（例: `$0.91`、`約921円`、`DL 284`、`4〜7月`）
- 円換算するなら **レートと日付** を一文で残す
- 取れない指標は **「未取得」**。推測で埋めない

### 一人称と時間

- 「〜と感じた」「手を止めていた」「請求は確認済み」など、主体と時点が分かる文
- 過去の自分の判断ミスや停滞を、一般論に薄めない

### 短く、仕事の言葉で

- 1文1メッセージ。修飾の山を作らない
- 専門語（AdMob、eCPM、ASO）は使ってよい。説明するなら **このサイトの文脈で一度だけ**
- 見出しは「何が書いてあるか」が分かること（「まとめ」「考察」だけにしない）

### 構成

- 冒頭3行以内に **結論（数字か状況）** を置く
- 表・リストは数字の整理に使う。雰囲気作りの箇条書きを増やさない
- FAQ は「読者が本当に聞きそうなこと」だけ。埋め草の FAQ を量産しない
- Keep / Problem / Try を使うなら **各1〜3行**。カタログにしない
- 免責は短く残してよい（誇大にしないため）

---

## 5. 記事タイプ別の最低ルール

| タイプ | 必須 | やりすぎ禁止 |
| --- | --- | --- |
| 収益報告 | 合計数字・前月／比較・根拠画面の有無 | 成功談への無理な着地、空の「来月こそ」 |
| 損益・コスト | 収益と出費を同じ単位で並べる。前提を表で明示 | 「投資対効果は高い」など根拠なしの評価 |
| How-to | 手順が再現できる。失敗しやすい点を1つ以上 | 「完全ガイド」化、アプリ宣伝だけの段落 |
| アプリ紹介 | 何のアプリか・誰向けか・ストアへの1導線 | 機能の美辞麗句リスト |
| 分析 | 仮説と「断定しない」を分ける | 一般論だけの長文 |

収益報告の手順・ファイル名は `playbooks/revenue-report.md` に従う。**文体はこのファイルが優先**する。

---

## 6. 公開前チェックリスト（毎回）

書き終わったら、次をすべて満たすこと。1つでもダメなら直す。

- [ ] 冒頭で、今回の結論が数字または具体状況で言えている
- [ ] 固有の数字／固有の出来事が本文に残っている
- [ ] 「誰の記事でも通じる」段落を消したか言い換えた
- [ ] 禁止リスト（§3）の語・締めがない
- [ ] 無いデータは捏造せず「未取得」等と書いてある
- [ ] 因果の断定を、データ以上に書いていない
- [ ] title / description が自然な日本語で、キーワードの羅列になっていない
- [ ] FAQ・カード・箇条書きが、埋め草になっていない

---

## 7. 良い例 / 悪い例

**悪い例**

> 個人開発で副業収益化を目指すうえで、継続的な改善とデータドリブンな意思決定が重要です。本記事では実践的なポイントを解説します。

**良い例**

> 2026年7月の AdMob 合計は $0.91 でした。6〜7月はアプリをほとんど触れず、その月の結果として読んでいます。

**悪い例**

> Cursor への投資は、長期的に見れば十分なリターンが見込めるでしょう。

**良い例**

> 4〜7月の AdMob は約921円、Cursor Pro+ と Apple 年会費（按分）だけで約4.3万円でした。広告収益では全くペイしていません。

---

## 8. エージェント向け（必須）

- ブログ記事の新規作成・大幅改稿の **最初のツール呼び出し前** に、このファイルを Read する
- 収益報告なら、続けて `playbooks/revenue-report.md` も読む
- 書き上がったら §6 のチェックリストを自分で通す（ユーザーに「確認して」と丸投げしない）
- 既存記事のトーンをコピーするときも、§3 の禁止に当たる文は引き継がない
